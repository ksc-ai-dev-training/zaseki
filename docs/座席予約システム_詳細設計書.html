1. はじめに

1.1 本書の位置づけ

基本設計書3章（データモデル）・4章（業務ルール・非機能要件の実現方針）で決めた方針を、実装に着手できるレベルまで具体化する。本章以降は「これを見れば作れる」状態を目指し、型・必須／任意・初期値・入出力の形まで決め切る。データ構造（2章 テーブル定義）は後から変更しづらいため、他の章より先に、最も慎重に決める。

1.2 対象読者

本システムを実装する開発者。基本設計書で決めた業務ルール・画面構成の「なぜ」まで遡って確認したい場合は、基本設計書・要件定義書を参照する（本書では「なぜ」の再掲は最小限にとどめ、要件定義書・基本設計書の該当箇所を参照する形をとる）。

1.3 技術スタック

要件定義書NFR-04（D7）のとおり、Keireki（AI開発\keireki）の実装方式に倣う：FastAPI＋asyncpg＋PostgreSQL、React 19＋TypeScript＋Vite＋Tailwind＋react-router＋SWR、Google OAuth2＋JWTセッション、/api/配下でのフロント・バック連携。本章のテーブル定義もPostgreSQLの型・機能（部分ユニークインデックス、JSONB等）を前提とする。

1.4 ID体系・トレーサビリティ

「この画面は何の要求から来たのか」を後から辿れるよう、Keireki同様のID体系を用いる。新しい要求・機能・画面・テーブル・APIを追加するときは、その時点で必ずIDを振り、関連ドキュメントの記述に括弧書きで添える（後から一括で付け直すのは大変なため）。

2. テーブル定義

2.1 共通ルール

  • 主キー: 全テーブル共通でid BIGINT（GENERATED ALWAYS AS IDENTITY）を主キーとする。以下の各テーブル定義では紙面の都合上、id行は省略し、id以外の列のみを記載する（すべてのテーブルの先頭にid BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITYがあるものとする）。
  • 作成・更新日時: 特記のない限り、全テーブルにcreated_at TIMESTAMPTZ NOT NULL DEFAULT now()を持つ。行の更新があり得るテーブル（状態が変化するテーブル）にはupdated_at TIMESTAMPTZ NOT NULL DEFAULT now()も持つ（アプリケーション側でUPDATE時に更新する）。これらも各テーブルの列一覧では省略し、テーブルごとの備考欄で「作成日時のみ」／「作成・更新日時とも持つ」を明記する。
  • 外部キーの削除方針: 特記のない限り、参照先の行は論理削除（deleted_atやstatus列）で扱い、外部キー制約にON DELETE CASCADEは使わない（誤操作による芋づる式の消失を避けるため）。物理DELETEを行う設計としたテーブル（T-04）は個別に明記する。
  • 真偽値・列挙値: 状態を表す列はVARCHAR＋アプリケーション層でのCHECK相当のバリデーションとする（DBのCHECK制約もあわせて張るが、値の追加・変更が今後あり得るため、アプリケーション層のバリデーションを主とする）。
  • 配列・複合値: 「曜日を複数選択」「座席IDの一覧」のように1列に複数の値を持たせる箇所はJSONB型とする（例: ["tue","thu"]）。正規化して別テーブルに分けるほどの検索要件がないため。

3. API設計

3.1 共通事項

  • ベースパス: すべて/api/配下（NFR-04）。本章のパスはベースパスからの相対で記載する。
  • 認証: 4.2節（認証・認可の実現方式）のとおり、HttpOnly CookieのセッションJWTで識別する。以下の一覧では「ログイン中の利用者本人」であること自体は前提とし、個別のAPIごとの認可条件（それ以上の権限が必要かどうか）のみを「認可」欄に記載する。認可条件の正式な一覧は5章（権限の判定）で改めてAPIごとに規定する。
  • 日付・日時の形式: 日付はYYYY-MM-DD（ISO 8601の日付部分）、日時はYYYY-MM-DDTHH:mm:ssZ（ISO 8601、UTC）とする。
  • 一覧系のページング: 本フェーズの想定規模（利用者約200名・座席約83席、要件定義書4章・6.1節）ではページングを必須としない。一覧APIは全件を返す（将来的にデータ量が増えた場合は個別に追加検討する）。
  • 更新系のレスポンス: 特記のない限り、作成・更新系のAPIは処理後の最新の行（またはリソース全体）をレスポンスとして返す。
  • エラーレスポンスの形式: 6章（エラー時の動き）で規定する。

4. 画面項目定義

4.1 本章の前提

画面のチェックはバックエンドの代わりにならない: 以下の入力チェックは、まず画面側で親切のために行うが、ブラウザの外からAPIを直接呼び出せば簡単に迂回できる。本章に記載した各チェックは、3章のAPIが受け取った時点でも必ず同様に検証する（実装上はバリデーションロジックを共有できる形にするとよい）。違反時のAPIの応答は6章で定義する。

S-01（ログイン）はGoogleログインボタンのみで入力フォームを持たないため、S-06（管理メニュー）は他画面への入口カードのみでやはり入力フォームを持たないため、いずれも本章の対象外とする。

項目種別必須入力チェック内容
氏名検索（新しく固定座席を指定する対象者の絞り込み）search任意特になし（部分一致検索）。一覧には固定座席を持たない利用者のみを表示する。

実際の座席番号の選択は、この画面には入力欄を持たず、「この人に固定座席を指定する」「座席を変更する」からS-02（空き状況・予約）のフロアマップへ遷移して行う（S-09の「座席の島を割り当てる」と同じ考え方）。S-02側での座席タップが実質的な入力にあたり、対象の座席がseat_type='fixed'かつ未割当であることをAPI側で検証する。

4.5 S-07 座席マスタ管理

項目種別必須入力チェック内容
座席番号検索／エリア／状態（一覧の絞り込み）search・select任意絞り込み条件であり入力チェックの対象外。
座席番号text必須全座席の中でユニークであること（T-03.seat_no UNIQUE）。新規追加時・編集時とも重複をAPI側でチェックする。
エリアselect必須NORTH／EAST／WESTのいずれか。
座席タイプselect必須フリー／固定／プロジェクトのいずれか。座席タイプの変更は、当該座席に予約・割当（T-04・T-07.allocated_seats）が存在する場合に業務上どう扱うかを個別に確認する必要がある（本フェーズでは編集時に警告を出すのみとし、強制的な整合性チェックは設けない。実装時に要検討）。
有効フラグtoggle必須（既定: 有効）オフにするとstatus='retired'（廃止、RULE-01）。廃止済み座席は空き状況・座席選択の対象から外れる。

4.6 S-08 権限・役割管理

項目種別必須入力チェック内容
氏名・メール検索／役割／在籍状況／退職済みを表示する（利用者一覧の絞り込み）search・select・checkbox任意絞り込み条件であり入力チェックの対象外。
氏名（姓・名）text × 2必須いずれも1文字以上。本人の自己変更ではなく管理部による訂正（D14）であることをAPI側の認可で担保する。
雇用形態select必須社員／契約職員／BPのいずれか。
管理部ロールを付与するtoggle必須（既定: オフ）オンでrole='admin'。自分自身のrole='admin'を自分でオフにできてしまうと管理部が誰もいなくなる恐れがあるため、「自分自身の管理部ロールを外す操作」はAPI側で拒否する（実装時の検討事項として明記）。
在籍状況select必須在籍中／休職中／退職済みのいずれか。「退職済み」への変更はRULE-06（4.1節）を発火させる重い操作のため、画面側で確認ダイアログを挟む（基本設計書のとおり）。
役割マスタのラベル（複数可）checkbox群任意役割マスタ（T-14）に存在するidのみ指定可能。権限判定には使わない（基本設計書4.2節）。
プロジェクト名text必須1文字以上。重複チェックは行わない（同名プロジェクトが存在してもよい、要件定義書に禁止規定なし）。
メンバー行ごとの役割（PM/PL/SL/なし）select必須（既定: なし）4つの選択肢のいずれか。人数の上限なし（PM・PL・SLとも複数名可）。
PJ席決担当radio（メンバー行ごと、単一選択）任意（プロジェクトに1名まで）役割がPMまたはPLの行のみ選択可（SL・なしの行はUIでdisabled）。プロジェクトにつき最大1名。API側でも役割がPM/PLでない利用者がproxy_user_idに指定されないよう検証する。
責任者（エリア）text（氏名検索）任意（未設定可）role='admin'の利用者のみ選択可（発注者確認済み、基本設計書3.2節T-02）。
副責任者（エリア）text（氏名検索）任意（未設定可）role='admin'の利用者のみ選択可。責任者が未設定の間は入力不可（画面側でdisabled、API側でも責任者未設定時は拒否）。
Slack通知先（Webhook URL）text任意入力する場合はhttps://hooks.slack.com/services/で始まるURL形式であることを確認する。未入力の場合は当該エリアへの通知を送信しない（FR-03-9）。
役割名（役割マスタ）text必須1文字以上、役割マスタ内でユニーク（T-14.name UNIQUE）。
説明（役割マスタ）text任意最大200文字程度（明確な上限は実装時に決定）。

4.7 S-09 プロジェクト座席（エリア担当）

項目種別必須入力チェック内容
担当エリアの選択（未割当プロジェクトの行）select必須NORTH／EAST／WESTのいずれか。「エリアを選択」（未選択）のまま送信不可。
必要座席数（修正）number必須1以上の整数。status='seats_allocated'（座席の島の割当済み）になった後は変更不可（API側で拒否）。
出社曜日の調整表・各セルcheckbox（プロジェクト×曜日）—各プロジェクト行について、確定曜日として送信できるのは全曜日のうちの任意の組み合わせ（第一・第二希望に限定しない、要件定義書FR-03-5の方針）。0曜日での確定が業務上意味を持つかは運用次第だが、システムとしては0曜日（曜日を1つも確定しない）確定操作自体はエラーにしない（実装時の要検討事項として残す）。
座席の島（範囲）の選択—（S-02のフロアマップから選択）必須必要座席数と一致する座席数を選ぶことを画面側で推奨表示するが、一致しなくても送信は妨げない（現地判断の余地を残す）。既に他プロジェクトへ割当済みの座席は選択肢から除外する（座席単位の判定、基本設計書3.3節）。

4.8 S-10 座席状況の履歴照会

項目種別必須入力チェック内容
照会する日付date必須直近1か月（D12、app_settings.seat_history_lookback_days）の範囲内であること。範囲外を指定した場合はエラー（6章）。未来日は指定不可（当日以前のみ）。

4.9 S-11 代理予約・取消

項目種別必須入力チェック内容
氏名検索（代理予約対象者の絞り込み）search任意特になし（部分一致検索）。一覧にはプロジェクトメンバー・固定座席利用者のいずれにも該当しない利用者のみ表示する。
氏名検索・座席種別・表示期間（代理取消対象の絞り込み）search・select・month × 2任意絞り込み条件であり入力チェックの対象外。

新規の代理予約は、この画面には座席選択の入力欄を持たず、「この人を代理予約する」からS-02のフロアマップへ遷移して行う（新規はフリー座席のみ、FR-01-5）。取消・解除は一覧から対象を選ぶ操作のみで、入力欄は持たない。
