1. はじめに

1.1 本書の位置づけ

基本設計書3章（データモデル）・4章（業務ルール・非機能要件の実現方針）で決めた方針を、実装に着手できるレベルまで具体化する。本章以降は「これを見れば作れる」状態を目指し、型・必須／任意・初期値・入出力の形まで決め切る。データ構造（2章 テーブル定義）は後から変更しづらいため、他の章より先に、最も慎重に決める。

1.2 対象読者

本システムを実装する開発者。基本設計書で決めた業務ルール・画面構成の「なぜ」まで遡って確認したい場合は、基本設計書・要件定義書を参照する（本書では「なぜ」の再掲は最小限にとどめ、要件定義書・基本設計書の該当箇所を参照する形をとる）。

1.3 技術スタック

要件定義書NFR-04（D7）のとおり、Keireki（AI開発\keireki）の実装方式に倣う：FastAPI＋asyncpg＋PostgreSQL、React 19＋TypeScript＋Vite＋Tailwind＋react-router＋SWR、Google OAuth2＋JWTセッション、/api/配下でのフロント・バック連携。本章のテーブル定義もPostgreSQLの型・機能（部分ユニークインデックス、JSONB等）を前提とする。

2. テーブル定義

2.1 共通ルール

  • 主キー: 全テーブル共通でid BIGINT（GENERATED ALWAYS AS IDENTITY）を主キーとする。以下の各テーブル定義では紙面の都合上、id行は省略し、id以外の列のみを記載する（すべてのテーブルの先頭にid BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITYがあるものとする）。
  • 作成・更新日時: 特記のない限り、全テーブルにcreated_at TIMESTAMPTZ NOT NULL DEFAULT now()を持つ。行の更新があり得るテーブル（状態が変化するテーブル）にはupdated_at TIMESTAMPTZ NOT NULL DEFAULT now()も持つ（アプリケーション側でUPDATE時に更新する）。これらも各テーブルの列一覧では省略し、テーブルごとの備考欄で「作成日時のみ」／「作成・更新日時とも持つ」を明記する。
  • 外部キーの削除方針: 特記のない限り、参照先の行は論理削除（deleted_atやstatus列）で扱い、外部キー制約にON DELETE CASCADEは使わない（誤操作による芋づる式の消失を避けるため）。物理DELETEを行う設計としたテーブル（T-04）は個別に明記する。
  • 真偽値・列挙値: 状態を表す列はVARCHAR＋アプリケーション層でのCHECK相当のバリデーションとする（DBのCHECK制約もあわせて張るが、値の追加・変更が今後あり得るため、アプリケーション層のバリデーションを主とする）。
  • 配列・複合値: 「曜日を複数選択」「座席IDの一覧」のように1列に複数の値を持たせる箇所はJSONB型とする（例: ["tue","thu"]）。正規化して別テーブルに分けるほどの検索要件がないため。

employment_typeVARCHAR(10)不可'employee'CHECK'employee' / 'contract' / 'bp'（社員／契約職員／BP）。管理部がS-08から設定（Googleログインでは取得不可）。

作成・更新日時: 作成・更新日時とも持つ（updated_atは氏名訂正・役割変更・在籍状況変更のたびにAPIが更新）。

2.16 T-16 app_settings（アプリケーション設定）

基本設計書4.6節で「Keirekiのapp_settingsに相当するテーブルを設ける想定」としていたが、テーブル定義が未確定だったため、本書で新設する（2026-08-26）。座席タイプ別サイクルの基準日・締切日、出社曜日アンケートのリマインド関連の設定値等、運用中に管理部が変更しうる値をハードコードせずに保持する。

列名型NULLデフォルトPK/FK/UNIQUE説明
keyVARCHAR(100)不可—PRIMARY KEY設定キー（例: project_seat_deadline_day）。本テーブルはid列を持たず、keyを主キーとする（2.1節の共通ルールの例外）。
valueTEXT不可—設定値。数値・文字列いずれもTEXTとして保持し、アプリケーション側で用途ごとにパースする。
descriptionTEXT可NULL設定内容の説明（管理画面での表示用）。

作成・更新日時: 作成・更新日時とも持つ。管理画面（設定変更UI）は本フェーズのスコープに含まれておらず、初期データ投入・DBへの直接更新で運用する（管理画面が必要になった場合は別途要件定義書・基本設計書を改訂する）。
