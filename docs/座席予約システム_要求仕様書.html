1. はじめに

1.1 背景

東京本社はフリーアドレス制を採用しており、全座席について事前予約を必要とする運用となっている。現在この予約はGoogleスプレッドシート「本社座席予約表」で管理されているが、月ごとにシートを作り直す運用負荷、同時編集による書き換え・上書きのリスク、スマートフォンからの操作性の悪さ、予約ルール（複数座席予約の禁止等）をシート上で機械的に担保できないといった課題がある。

1.2 目的

現行スプレッドシートで行っている座席予約業務をWebシステム「本社座席予約システム（コードネーム: Zaseki）」に移行し、社員が出社前にスマートフォンから座席を予約できる状態を実現することを目的とする。

1.3 本書の位置づけ

本書は、発注者が本システムに対して「何をしてほしいか」を要求として示すものである。要求をどのように実現するかの要件定義・設計は、後続の要件定義書・基本設計書にて行う。本書では実現方式・画面構成・データ構造は規定しない。

2. システム化の対象と範囲

2.1 対象業務

  • 座席の予約・確認・取消
  • 固定座席・プロジェクト座席の予約（管理部・エリア責任者・PM による代理予約を含む）
  • 日付ごとの座席の空き状況の確認
  • 座席・エリアのマスタ管理（フロアレイアウト変更への追従）

2.2 対象外

以下は本システムの対象外とし、システム化の範囲に含めない。

  • 会議室の予約（Googleカレンダーで管理中）
  • 勤怠管理・出社実績の集計（予約実績の参照までを対象とし、勤怠との突合は行わない）
  • 入退室管理（入室権限そのものの管理）
  • 東京本社以外の拠点の座席管理
  • ロッカー・キャビネット・備品の管理

3. 要求事項

3.1 機能要求

要求ID要求説明
REQ-F-01 現在スプレッドシートで管理している座席予約と同等のことができること 日付ごとに、どの座席を誰が使うかを登録・変更・取消・参照できること。現行の座席予約表で行っている運用が、移行によって損なわれないことを求める。
現行表: 本社座席予約表
REQ-F-02 スマートフォンから座席を予約できること 出社前・移動中に予約や取消ができること。社員が日常的に使う主たる操作（空き確認・予約・取消）が、スマートフォンの画面で無理なく完結すること。
REQ-F-03 固定座席や周期的な座席確保を簡単に行えること 「毎日」「毎週火・木」のように繰り返し利用する座席を、日ごとに1件ずつ登録しなくても一括で確保できること。現行運用では固定座席利用者やプロジェクト座席が多数を占めており、この登録の手間を減らすことを特に重視する。あわせて、確保済みの周期予約の一部の日だけを取り消せること。
REQ-F-04 座席の空き状況が一目でわかること 指定した日付について、どの座席が空いているかを利用者が判断できること。エリア・座席の位置関係が把握できる見せ方が望ましい。
REQ-F-05 座席利用ルールをシステムで担保できること 「使用しない座席の予約」「複数座席の予約（固定座席利用者を除く）」「入室権限がないフロアの予約」といった現行ルールに反する予約を、システム側で抑止できること。
REQ-F-06 座席・エリアの構成を管理者が変更できること フロアレイアウトやエリア分けは過去に複数回変更されており、今後も変更される。座席の追加・削除・エリア変更・座席タイプの変更を、開発者の作業を介さず管理部が行えること。

3.2 非機能要求

要求ID要求説明
REQ-N-01 Google認証により当社のGoogleアカウント保有者しか利用できないこと 当社はGoogle Workspaceを利用している。追加のID管理を発生させず、許可ドメインのGoogleアカウントを持つ利用者以外はアクセスできない仕組みとすること。
REQ-N-02 役割により操作範囲を制御できること 一般利用者は自分の予約のみ、管理部・エリア責任者・PM は担当範囲の他者分の予約も行える、といった役割に応じた制御ができること。
REQ-N-03 同じ座席が二重に予約されないこと 複数の利用者が同時に操作しても、同一日・同一座席の予約が重複して成立しないこと。現行スプレッドシートの同時編集で起きうる上書きの問題を解消すること。
REQ-N-04 既存システム（LCC CRM）の技術構成を踏襲すること 社内で運用実績のあるLCC CRMと同一の技術スタック・構成とすることで、保守要員のスキル共通化と運用ノウハウの再利用を図ること。

4. 制約条件

  • 技術構成: 既存システムLCC CRMの技術構成を踏襲すること（REQ-N-04）。独自の技術選定は行わない。
  • 認証基盤: 認証はGoogleアカウント（許可ドメイン: kogasoftware.com）を前提とすること。
  • 利用者: 社員のほか、契約職員・臨時職員・BP も利用する。社員番号を持たない利用者（BP 等）が存在する。
  • 利用規模: 東京本社の座席は約70席、利用者は200名程度。朝の出社前後に利用が集中する。
  • 運用ルール: 現行の「東京本社の座席利用について」（座席予約表の運用ルールシート）に定めるルールを前提とすること。

5. 前提条件・留意事項

  • 座席・エリアの構成、予約項目は、現行の 本社座席予約表 の内容に基づく。運用ルールは同ファイル内のルールシートを参照すること。
  • 本システムは社内利用を前提とし、社外への公開は行わない。
  • 現行スプレッドシートからの過去予約データの移行の要否は、別途協議する。
  • 現行の座席利用フロー（前月25日までに固定座席・プロジェクト座席、26日以降にフリー座席）を維持するか見直すかは、要求定義フェーズで整理する。
研修での進め方について
本書は「何をしてほしいか」までを示すものであり、画面構成・データ構造・実現方式は意図的に記載していない。それらをどう決めるかが要求定義以降の作業となる。判断に迷う点は、まずAIに相談し、それでも決まらないものはSlack「ai開発研修」チャンネルで質問すること。

6. 用語定義

用語定義
フリーアドレス社員の座席を固定せず、出社日ごとに空いている座席を利用する働き方。
固定座席利用者を固定した座席。利用者は管理部が出社実績・必要性等を考慮して決定し、管理部が予約を行う。
プロジェクト座席プロジェクトに割り当てた座席。エリア責任者が出社曜日と座席を決定し、PM（PL）が予約を行う。

エリア責任者 / 副責任者エリアの座席管理に責任を負う担当者。責任者は管理部が任命し、副責任者は責任者が任命する。
座席番号座席を識別する記号（A1、C4、M7 等）。
周期的な座席確保「毎日」「毎週火・木」のように、繰り返しの規則を指定して複数日分の座席を一括で確保すること。
BPビジネスパートナー。社員番号を持たないが座席を利用する。
許可ドメインログインを許可するGoogleアカウントのメールドメイン（kogasoftware.com）。
LCC CRM社内で運用中の既存システム。本システムはその技術構成を踏襲する。
